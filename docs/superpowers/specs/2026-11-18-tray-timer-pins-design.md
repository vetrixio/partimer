# 系統匣選單計時與專案釘選 設計文件

- 日期：2026-11-18
- 狀態：待使用者審閱（已經過一次實作者視角的審查）
- 標示說明：**〔使用者決定〕** 是使用者明確說的；**〔設計者決定〕** 是撰寫者的判斷，使用者可推翻；**〔實作者決定〕** 留給實作者自行判斷。
- 前一份設計：`docs/superpowers/specs/2026-11-06-partimer-design.md`（以下稱「主設計」）。本文未提到的規則一律沿用主設計。

## 1. 為什麼要做

Ubuntu 的系統匣（AppIndicator）收不到左鍵點擊，點圖示只會出現選單。現在要開始計時得「點圖示 → 打開面板 → 按 START」。使用者要**直接在系統匣選單上開始、暫停、停止計時和換專案，不必打開面板**〔使用者決定〕。

專案可能很多，全部列在選單上會太長，所以加上「釘選」：**只有釘選的專案會出現在選單上，同時釘選的數量有上限**〔使用者決定〕。

### 目標

- 沒在計時：從選單點一個釘選專案就開始計時。
- 計時中：從選單暫停／繼續、停止計時，或點另一個釘選專案換過去（先確認）。
- 選單隨時反映目前狀態：其他視窗（面板、紀錄、設定、轉入、匯入 CSV）改了資料，選單最晚約 1 秒後跟上。
- 從選單操作與在面板上操作的結果相同：同樣的紀錄、同樣的活動紀錄、面板和其他視窗立即更新。

### 非目標

- 選單上不顯示跳動的計時時間（圖示旁的標題和提示文字已經有）〔設計者決定〕。
- 選單上不能新增專案、不能填標題或內容（要填請開面板）。
- 面板的專案選單不因釘選而改變排序或外觀〔設計者決定〕。
- 不提供釘選順序的手動排序。

### 反目標（做了反而失敗）

- 從選單停止或換專案時，面板上已經打好但還沒按儲存的文字不見了。
- 選單項目和實際狀態不一致（例如已經停止了，選單還顯示「停止計時」），或點了沒反應也沒說明。
- 選單每秒閃一下或自己關掉（只在內容真的變了才重建）。

## 2. 平台

macOS、Windows、Ubuntu 都加〔設計者決定，使用者未反對〕：macOS／Windows 是右鍵選單（macOS 左鍵也可能出選單，依現狀），Ubuntu 是唯一的選單。三個平台用同一份選單內容。

## 3. 釘選

### 3.1 資料

- 每個專案多一個布林欄位 `pinned`（JSON 欄位名 `pinned`，預設 `false`，讀不到視為 `false`）〔設計者決定〕。
- **不升資料版本**：`Project` 有 `#[serde(flatten)] extra`，v0.1.5 讀到 `pinned` 會原樣保留、照樣存回，不會出錯也不會刪掉。轉移檔自動帶著釘選狀態；CSV 不含釘選（CSV 匯入的專案都是未釘選）。
- 舊版（v0.1.5 以前）在已釘選的專案上按「封存」不會取消釘選，所以資料裡可能出現「已封存但 `pinned: true`」的專案。下面的「有效釘選」規則讓這種資料自然被忽略，不需要修正資料。

### 3.2 有效釘選與上限

- **有效釘選** = `pinned` 為真、專案未封存、所屬客戶未封存（也就是面板專案選單裡看得到的專案）。
- 上限 **5 個**〔設計者決定，使用者同意〕，以「有效釘選」計數。
- 釘選第 6 個時拒絕，訊息：「最多釘選 5 個，請先取消一個」。
- 已封存的專案（或所屬客戶已封存）不能釘選，訊息：「已封存的專案不能釘選」。
- 若資料裡的有效釘選超過 5 個（手改資料或轉入），不自動修正：選單只列前 5 個（依 §4.4 的順序），設定視窗照實顯示全部，且在數量降到 5 以下前不能再釘選新的〔設計者決定〕。

### 3.3 封存與刪除

- 封存專案時把它的 `pinned` 設為 `false`；封存客戶時，把該客戶底下所有專案的 `pinned` 設為 `false`〔設計者決定，使用者同意〕。取消封存**不會**恢復釘選。
- 刪除專案（或客戶）時，釘選隨著專案一起消失，不需要特別處理。
- 改名、改顏色不影響釘選；選單上的名稱跟著更新。

### 3.4 設定視窗

- 「客戶與專案」每個專案列多一個釘選切換按鈕（例如「釘選」／「已釘選」，或圖釘圖示加上文字說明；外觀〔實作者決定〕，但要能用鍵盤操作、有可讀的 `aria-label`／`aria-pressed`）。
- 已封存的專案（或所屬客戶已封存）按鈕停用。
- 區塊標題旁顯示「已釘選 N／5」〔設計者決定〕。
- 失敗（超過上限等）的訊息顯示在該區塊現有的錯誤位置，與改名、封存的錯誤一致。
- 釘選變更和其他目錄變更一樣寫入活動紀錄（新增動作 `PIN`／`UNPIN`，或沿用目錄變更的既有動作；〔實作者決定〕，但要能從活動紀錄看出哪個專案被釘選或取消）。

## 4. 系統匣選單

### 4.1 沒在計時

```
▶ 客戶A・網站改版
▶ 客戶A・維護
▶ 客戶B・App
──────────
打開面板
紀錄
設定
──────────
結束
```

- 每個有效釘選專案一行，文字為「▶ 客戶・專案」。
- 沒有任何有效釘選時，第一段改成一行**停用**（灰字）的項目：「到設定釘選專案，就能從這裡開始計時」。
- 最下面的「結束」是關閉 app（維持現狀）。計時用的叫「停止計時」，不叫「結束」〔設計者決定，使用者同意〕。

### 4.2 計時中／暫停中

```
計時中：客戶A・網站改版      ← 停用，只顯示
暫停                         ← 暫停中顯示「繼續」，第一行改為「暫停中：…」
停止計時
──────────
改記其他專案：               ← 停用，只顯示
▶ 客戶A・維護
▶ 客戶B・App
──────────
打開面板
紀錄
設定
──────────
結束
```

- 正在記的專案不出現在「改記其他專案」底下（即使它有釘選）。
- 正在記的專案可能沒有釘選、或已封存（計時中被封存）；第一行照樣顯示它的名稱。
- 「改記其他專案」底下沒有任何項目時（沒有其他有效釘選），整段（含標題與上方分隔線）省略〔設計者決定〕。

### 4.3 名稱顯示

- 「客戶・專案」與面板今日紀錄的寫法相同。
- 名稱必須照字面顯示：選單元件（muda）把 `&` 當作快捷鍵記號，Linux 的 GTK 選單把 `_` 當作快捷鍵記號。實作要確保含 `&`、`_` 的名稱顯示正確（例如依 muda 的規則跳脫），並在 Ubuntu 實機確認〔實作者決定方式〕。
- 名稱很長時截斷並加「…」，上限〔實作者決定〕（建議約 40 個字元），避免選單比螢幕還寬。

### 4.4 順序

依面板專案選單的順序（客戶順序，再到客戶內的專案順序）〔設計者決定〕。

### 4.5 更新方式

- 選單內容由一個純函式從 `Session` 的資料算出（以下稱「選單模型」）：狀態（沒在計時／計時中／暫停中）、目前的專案名稱、可點選的釘選專案（id 與顯示文字）。這個函式放在 `partimer-core`，不依賴 Tauri，可直接寫單元測試〔設計者決定〕。
- `ticker` 每秒的 `tick` 已經讀取 `panel_state` 並呼叫 `tray::update`；同一處算出選單模型，**和上一次不同才**用 `set_menu` 換掉整份選單（muda 0.20 的選單項目不能隱藏，只能換整份）。與現有 `Shown::apply` 的比對方式相同。
- 選單動作完成後應立即更新選單，不必等下一秒（〔實作者決定〕怎麼觸發，例如動作後直接呼叫同一個更新函式）。
- 不採用「每個改資料的地方都通知選單」：改資料的路徑太多，漏一個選單就過時。

## 5. 選單動作

所有動作都在 Rust 端完成，不經過面板；成功後與現有 command 一樣廣播 `state-changed`（`commands::changed`），讓面板、紀錄視窗、小時鐘立即更新。動作在 session 鎖內完成，**對話框期間不持有鎖**（同 `src-tauri/src/moving.rs` 的做法）。

### 5.0 點擊時以「當下的實際狀態」為準

選單最多可能落後 1 秒，而 Ubuntu 上打開著的選單不會跟著變，所以使用者可能點到已經過時的項目。處理方式〔設計者決定〕：每個動作都依**點擊當下的實際狀態**決定要做什麼，而不是依選單畫出來時的狀態。

- 點釘選專案（不論它是畫在「沒在計時」還是「改記其他專案」底下）：
  - 現在沒在計時 → §5.1 開始。
  - 現在正在記這個專案 → 什麼都不做。
  - 現在正在記別的專案 → §5.4 改記（先確認）。
- 點「暫停」時已經暫停、點「繼續」時已經在計時 → 什麼都不做。
- 點「停止計時」、「暫停」、「繼續」時已經沒在計時 → 什麼都不做（不跳通知，因為使用者要的結果已經成立）。

實作上，釘選專案的點擊是同一個動作（依狀態分支），不要分成「開始」與「改記」兩種項目 id。

### 5.1 開始（沒在計時時點釘選專案）

效果等同「在面板選這個專案，再按 START」〔設計者決定〕：

- 用 session 的草稿（面板同步到後端的標題與內容）呼叫既有的 `select_project`，再用選完後的草稿呼叫 `start`。
- 因此：點的是面板目前選的專案時，面板上打好的標題、內容會成為這筆的標題與內容；點的是別的專案時，標題換成該專案上一筆的標題，內容沿用（與面板切換專案的規則相同）。
- 不需要確認框。

### 5.2 暫停／繼續

呼叫既有的 `pause`／`resume`。不需要確認框。

### 5.3 停止計時

- 寫入的標題與內容：沒有「草稿衝突」時用 session 的草稿（也就是面板上目前的文字，含未儲存的部分）；有草稿衝突時（計時中的那筆已在紀錄視窗被修改、面板有未儲存的文字）用**紀錄裡現有的文字**，與 `flush_on_exit` 的規則相同〔設計者決定〕。
- 暫停中停止，結束時間是暫停那一刻（沿用既有 `stop` 的行為）。
- 不需要確認框（與面板 STOP 一致）。

### 5.4 改記其他專案（計時中點另一個釘選專案）

- 先顯示原生確認框，文字與面板相同：「結束目前這筆，改記另一個專案？」，按鈕「結束並切換」／「取消」〔使用者同意〕。
- 確認後：目前這筆用 §5.3 的規則寫入文字並結束，馬上開始新專案（標題為該專案上一筆的標題、內容空白），即既有 `select_project` 計時中的分支，只是文字來源依 §5.3。
- 確認框顯示期間狀態可能已變（例如在面板上按了 STOP、或計時中的專案已換掉）。確認後要重新檢查：若已不在計時，或目前的專案不是確認框出現時的那個，就不做任何事〔設計者決定〕。
- 若點的專案在確認期間被封存或刪除，沿用既有錯誤處理（見 §5.5）。

### 5.5 失敗時

- 任何動作失敗（例如專案剛被封存或刪除、已經沒在計時），以系統通知顯示錯誤訊息（`ticker` 已有的通知機制），選單照常更新為實際狀態〔設計者決定〕。
- 存檔失敗（`save_blocked` 或寫入錯誤）沿用既有行為：記憶體裡的狀態照樣改變，面板顯示存檔錯誤提示，背景每秒重試。

### 5.6 限制

- 面板每打一個字就會立刻把標題與內容同步到後端（`DraftFields.svelte` 的 `sync` → `set_draft`，沒有延遲合併），所以選單動作拿到的就是面板上的文字，不需要先叫面板送一次。
- 唯一例外：面板上用中文輸入法**正在組字、還沒送出**的文字不會被帶到（組字期間不同步）。這是已知限制，寫進驗證清單說明。
- 12 小時提醒仍然只出現在面板與系統通知；選單不另外顯示。

## 6. 測試

- `partimer-core`：
  - 釘選：上限 5（第 6 個被拒、訊息正確）、已封存專案不能釘、封存專案／封存客戶會取消釘選、取消封存不恢復、刪除後不再計數、有效釘選不含已封存的。
  - 讀寫相容：沒有 `pinned` 欄位的舊資料讀成 `false`；已封存但 `pinned: true` 的資料不算有效釘選、不出現在選單。
  - 選單模型：三種狀態的內容；正在記的專案不出現在可點清單；沒有釘選時的提示；超過 5 個只取前 5；順序與面板一致。
  - 動作：選單開始用草稿；停止時有／無草稿衝突的文字來源；改記時文字來源與新專案的標題；確認後狀態已變則不動作。
- `src-tauri`：選單模型轉成選單項目的部分（項目 id 與文字、停用狀態、`&`／`_` 跳脫）盡量做成可測的純函式。
- 前端：釘選按鈕狀態與「已釘選 N／5」若有可抽出的純邏輯就加測試；`npm run check` 通過。

- `README.md`：說明釘選與從系統匣選單計時。
- 主設計中描述系統匣選單的段落補上新項目。
- `docs/verification-checklist.md`：新增實機確認項目，至少包含：三平台選單內容與狀態切換、Ubuntu 上從選單開始／暫停／停止／改記、面板開著與關著時的文字寫入（含草稿衝突）、含 `&`／`_` 的專案名稱、設定視窗釘選上限與封存取消釘選。
- `CHANGELOG.md`：發版時寫入。

## 8. 考慮過的做法

1. **每秒算選單模型、有變才整份重建**（採用）：一處涵蓋所有改資料的路徑，最多延遲 1 秒；平常不重建，不會閃。
2. **固定選單、只改文字與停用狀態**：muda 0.20 的 `MenuItem` 只有 `set_text`／`set_enabled`，不能隱藏，無法表達「暫停／繼續」「改記」段落的出現與消失。不採用。
3. **每個改資料的地方都通知選單更新**：改資料的路徑很多（面板、紀錄、設定、轉入、匯入 CSV、自動結束），容易漏。不採用。

選單上的專案範圍也考慮過「只顯示上次的專案」與「列出全部專案」，使用者選了「列出專案＋釘選＋上限」〔使用者決定〕。

## 9. 留給實作者

已知的實作注意事項（審查時確認過）：

- 系統匣選單事件在主執行緒上觸發；原生確認框（`blocking_show`）不能在主執行緒上等待，要在另開的執行緒裡顯示，等待期間不持有 session 鎖。
- `CatalogView` 要帶出每個專案的 `pinned`，設定視窗才能顯示。
- §5.3 有草稿衝突時需要「計時中那筆的現有標題與內容」，可在 core 加一個小的輔助函式。

其餘由實作者決定：

- 釘選按鈕的外觀與文字。
- 活動紀錄是否新增 `PIN`／`UNPIN` 動作（要能看出是哪個專案）。
- 名稱截斷長度與跳脫方式。
- 選單動作後立即更新的觸發方式。
- 選單項目 id 的格式（例如 `pin:<專案 id>`）。
